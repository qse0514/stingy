**本次做了什么：**

1. **定位了一个架构级缺陷**（学员发现，DB 实证于会话 #8）：HITL 确认路径（`POST /api/chat/confirm`）刻意不经过 runAgent —— 这是对的 —— 但它也不写 `messages` 表，模型记忆停在"待确认…尚未记入"。于是用户确认后追问，模型要么说"没记上"（反向谎报，trace 34623773），要么重新提交（trace eb570701，靠 10 分钟幂等窗口才没重复记账）。根因一句话：**状态变了，记忆没人通知 —— 三层各自都对，接缝漏了**。

2. **修复（三处，都有注释说明来龙去脉）：**
   - `server/src/services/pending.ts` 新增 `syncMemoryReceipt`：confirm/reject 时①整句重写那张"待确认"回执（拔锚，不追加——错误文本留上下文就是锚）+ ②会话末尾追加成对【申请表+新回执】（只做①不够：模型自己的旧正文排在后面，就近锚定赢了重写；孤儿 tool 行会让 API 400，必须成对）。
   - `server/src/services/audit.ts`：`Verdict` 增加 `recordedFact`；规则⑤触发时 reflect 改用"以已落库事实为准"话术（旧话术"如实说你还没执行"对反向谎报方向相反，拦了等于没拦）；规则③先查 `hasRecentConfirmed()` 再定罪（否则确认后诚实的"记好了"被误报）。
   - 新实验脚本 `npm run exp:confirmsync`（走真实记忆层复现事故），已挂进 package.json。

3. **验证状态（都真跑过）**：`exp:confirmsync` 2/2 通过；`exp:afterconfirm` 回归通过；前后端 `tsc --noEmit` 均 0 错误。问题与 4 个踩坑记录在 `docs/devlog/week12-day1-questions.md`（当天上午是 Memory 中期/buildHistory，下午是本修复——同一条线）。
