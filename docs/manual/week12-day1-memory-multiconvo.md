## 一、traces 无上限（⑥）

一天手测 244 行，W12 是 4 Agent × 24 站全自动 —— 必须有上限。两个决定：

1. **按案卷删不按行删**：被腰斩的案卷（只剩后半段）长得就像"这次一个工具都没调"，正是对账规则③⑤要抓的形状 —— 删一半等于制造假证据。
2. **确定性计数器触发**：每 20 次开卷清一次（`startTrace`），不用概率（"不要把触发条件交给概率"）、不用 cron（部署环境未定）。重启后第一次开卷必清 → 进程一重启就收敛。

细节：`DELETE ... NOT IN (子查询)` 要再包一层派生表（MySQL 不许边删边读同一张表）；排序用 `MAX(id)` 不用 `created_at`（同一秒分不出先后）。函数名叫 `startTrace` 不叫 `newTraceId` —— **有副作用的函数名字必须诚实**。

## 二、改 / 删 / 恢复（②）

### 一条 UPDATE 的三分结局（mysql2 实测）

| (affectedRows, changedRows) | 含义 |
|---|---|
| (0, 0) | 这个 id 根本没有 |
| (1, 0) | 找到了但值没变 |
| (1, 1) | 真改了 |

`(1,0)` 是免费的幂等回执 —— **但只在 delete 里**（删过又删 = 前一次真发生过）。照抄到 restore 里就是事故：没删过的记录回"已恢复…本来就没删" → "已"开头 → 模型和对账双双当成功（乱恢复 #31 的第 4 环）。修正：`未恢复（#id）：当前不处于删除状态`。⚠️ 不能说"从未删过"——库里只有 `deleted_at` 一列，**一列状态记不下历史**。

### 防绕过：新写路径要重审所有旧关卡

`add_expense` 超 5000 转提案，但如果 `update_expense` 放行任意金额：先记 10 元（自动过）→ 改成 100 万（自动过）= HITL 整个被绕开。修法不是在 update 里再写一遍风控（两处重复），而是**堵死这条路逼回已有关卡**：超阈值拒绝修改，让用户删了重记 —— 重记必然撞确认流程。

### 软删（deleted_at）与"可逆"

删除不走 HITL —— 但理由不是"软删可逆"（循环论证：可逆若靠进库敲 SQL，那正是要修的病），而是 D5 三条真理由（校验重复/双击/失去对账）在删除上一条不成立。代价是"可逆"必须兑现成产品动作三件套（见速查）。软删补丁只有 **2 处**：queryExpenses 公用 where 数组 + addExpense 幂等查重（已删的 10 分钟内可重新记 —— 同 rejected 不去重：用户改主意应该能记）。

## 三、Memory 中期 + 多会话（③）

### 所有权翻转

```
以前：前端 React state 持有全量历史 → 每次全量寄 → 后端用完就扔
现在：messages 表持有（含申请表+回执）→ 前端只寄 {conversationId, message}
```

一刀解决三病：刷新即死 / #38 失忆（回执活不过请求边界）/ 前端可伪造历史（红队洞）。

### buildHistory：唯一有脑子的函数

三步：SQL 取最近 30 条（里层 DESC LIMIT 切最近、外层翻回正序）→ **对齐截断**（从头丢到首条是 user，防孤儿申请表/回执 —— 孤儿回执开头 API 直接 400）→ 逐行翻回 OpenAI 形状（`tool_calls` 存原文此刻才 parse）。

### history vs transcript（最容易混）

```
history    = system + 库里30条 + 本轮新增 + reflect纠正   ← 本次调用的工作台，用完扔
transcript = 只有本轮新产生的申请表+回执                   ← 要归档进记忆的部分
```

不进记忆的五样：system prompt（配置）、旧历史（库里已有）、**草稿**（锚定 3/3 vs 2/3）、reflect 纠正（判决书，存了变锚）、炸掉时说一半的话。但 **catch 里 transcript 照落** —— 回执是已发生的事实，不落就又是 #38。

### persistTranscript 的两个机关

- `for + await` 顺序写入，不用 `Promise.all`：插入顺序 = 自增 id 顺序 = 重放顺序（顺序敏感第 8 例：行都对，时序错了就死）
- 落完 `transcript = null`：成功落库后若后续步骤炸了，catch 不会重复归档 —— 幂等思想在 controller 的小复用

### HITL 确认回写（下午修复，另一会话完成）

confirm 是全系统唯一不经过 runAgent 的状态变更路径 → 也是唯一忘了通知记忆的路径。修法 `syncMemoryReceipt`：①整句重写旧"待确认"回执（拔锚）+ ②会话末尾追加成对申请表+回执（真相必须同时是**可信通道**和**最新一句**）。**每一条状态变更路径都要问：谁的记忆需要知道这件事？**

## 四、当天两场 debug（方法论）

**乱恢复 #31（四环链）**：回执没记忆 → 纠正无效（零工具路上没回执可"以其为准"，且流式轮不传 tools 想补调也不行）→ 恢复没眼睛（查账滤掉已删）→ 幂等回执骗过对账。每环一个修：Memory 落库 / 零工具专属话术 / `deleted:true` 参数 / "未恢复"第三结局。

**exp:crud 23/24（环境耦合）**：规则③加了 `hasRecentConfirmed()` 前置查询后，实验断言被自造的 confirmed 提案安抚。⭐ 新规矩（architecture.md 不变量 9）：**给对账规则加环境依赖（查真库/查时间）时，测这条规则的实验也在爆炸半径里。** 配套方法论：每条补丁配对照组，证明断言那句话真有杀伤力。

## 五、Planning：为什么 Stingy 不做（学员的论证）

四判据：步数>3 且有依赖 / 错路代价高 / 人需预审意图 / 需要预算 —— Stingy 全不沾（最重任务 2-3 步、读免费写有兜底、没人想审批记账、5 轮没真撞过）；F1 车队经理全沾。且给 Stingy 加计划确认 = 把 HITL 关卡从信息最完整处（工具内，手握结构化数字）搬回最早处（只有自然语言）—— 倒退。**教学清单上的能力 ≠ 产品需要的功能**（系列第二问；第一问是 D5 的 multi-agent）。
